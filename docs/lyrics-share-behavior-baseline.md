第一批只增加测试与这份基线，不修改业务实现、UI、数据库或配置格式。目的是固定后续简化需要保留的行为，并将已确认的问题和目标行为写成可执行断言。第一批结果保留如下；后续批次的进展记录在文末。

## 生命周期约定

| 操作 | 生命周期与顺序 | 结果可以影响的范围 |
| --- | --- | --- |
| 初始化、字体列表、实时预览 | 属于当前分享会话；关闭或切歌时取消，晚到结果不得回写 | 当前歌曲、当前会话及对应内容版本 |
| 选句、清空、模板、字体选择 | 点击提交复制／保存前，先接受之前的编辑；不等待预览或偏好写入 | 当前草稿；已提交导出的内容不随编辑改变 |
| 字体偏好写入 | 已接受的用户选择应保留；连续选择最终以最后一次为准 | 持久化偏好；旧写入结果不得恢复旧草稿 |
| 图片／文字复制 | 共用一条 FIFO 队列，图片生成也在顺序内；提交后独立完成 | 剪贴板按提交顺序更新；旧请求不结束新请求的忙碌状态 |
| 图片保存 | 单独一条 FIFO 队列，与复制互不阻塞；提交后独立完成 | 保存提交时的内容和文件名；旧请求不覆盖新会话 |
| Store 释放 | 取消会话任务和导出任务；不启动排队中的写入 | 不提供跨进程恢复保证 |

失败或取消保存对话框不能阻断后续队列；同一内容的待完成保存仍去重，失败后允许重试。旧导出结果沿用 `operationNotices`，当前请求仍通过分享状态反馈。初始化未完成时暂不接受编辑和导出。上述 UI 行为沿用既有约定。

## 第二批：统一状态入口和编辑顺序

2026-10-23 完成，生产代码只涉及 `player:core`：

- `PlayerLyricsShare.kt` 集中处理分享事件、会话、草稿和异步回调；通过回调更新 Store 持有的同一个 `PlayerState`，不增加另一套可变 UI 状态。
- `PlayerStore` 转发分享事件，继续提供播放上下文、共享操作编号和搜索互斥边界。UI 现有读取接口及同步开关会话的行为保留。
- 字体与选句、清空、模板一样，在 dispatch 返回前更新草稿；复制／保存因此能捕获前一笔字体编辑，不必等待偏好写入或预览。
- 已提交字体选择通过 Store 生命周期内的 FIFO 通道持久化；关闭和切歌不取消，释放 Store 会取消。成功不回写草稿，失败仅反馈到仍匹配的会话和选择版本；重选同一字体可重试。
- 初始化／字体列表中的自动偏好纠正也经过同一写入通道，但继续绑定原会话。这样既不会插入先前连续提交的用户选择之间，也不会让关闭会话后尚未开始的自动纠正落盘。
- 选择版本随所选字体在 `PlayerState` 的同一次原子更新中发布。迟到的字体列表可填充当前缓存，但不能恢复旧选择；旧预览和旧失败反馈在 CAS 重试后仍须重新检查当前状态。

原有预览生成、复制／保存算法随代码归属原样迁入控制器；复制与保存仍是两条独立 FIFO。预览重建条件仍保留原实现，本批不处理“生成中不结束”的已知问题。任务生命周期的进一步统一和导出执行器拆分留给后续批次。页面、数据库及持久化配置格式未改。

## 第三批：统一分享会话、字体加载和预览生命周期

2026-10-23 完成。生产代码仍仅涉及 `player:core`，页面、数据库和配置格式未改。

- `LyricsShareTasks` 为每次分享创建同一个父任务，分别管理初始化、字体列表和预览任务。关闭、切歌或 Store 释放会取消这些任务；替代预览取消前一个预览，不等待不响应取消的平台调用。
- 初始化与字体加载的请求编号也进入 `PlayerState`。结果接收和结束忙碌状态都在原子更新中检查会话、歌曲及请求编号；旧任务的 `finally` 不能结束新任务。移除控制器外置的字体加载代数。
- 字体加载完成后，依据最新选句、模板、字体和歌曲内容决定预览重建；不再使用加载开始时的选择。初始化期间失效字体缓存会替换初始化任务，旧结果不能恢复旧状态。
- 用完整 `LyricsShareCardModel` 记录已生成图片的内容，字体、模板读取值由这个模型派生；预览有效性还检查选句。歌曲标题、歌手、封面／封面缓存键和歌词正文变化都会使旧图片失效，并为当前会话安排新预览。播放进度变化不触发重建。
- 编辑后的新预览生成期间继续显示旧图片；清空选句立即清空图片。返回失败或直接抛出异常都会结束对应忙碌状态并允许重试；初始化异常结束当前会话并通过现有消息接口反馈。
- 复制、保存和已提交用户字体偏好的执行逻辑与第二批保持一致。复制／保存仍使用两个独立 FIFO，并保留提交内容捕获、独立完成、失败重试和新歌曲／新会话隔离。

## 第四批：拆分复制与保存的导出执行器

2026-10-23 完成。生产代码只调整 `PlayerLyricsShare.kt` 并新增 `LyricsShareExportExecutor.kt`；第三批的初始化、字体、编辑和预览处理保持不变。

- 每个分享控制器创建一个导出执行器，直接使用 Store 的协程作用域。图片／文字复制共用一个 FIFO，图片生成也在队列内；图片保存使用另一个 FIFO。两条队列互不阻塞。
- 执行器只处理已捕获的请求，不读取或修改 `PlayerState`。控制器继续同步捕获歌曲、会话、请求编号、文字／完整图片模型、预览字节副本，并在提交时固定保存文件名；请求编号先发布，再入队。
- 关闭分享、切歌和重开会话只结束可取消的会话任务，已提交导出继续执行。Store 释放时取消两个执行任务，任务完成钩子清除剩余排队请求，包括协程尚未开始运行就被取消的情况。
- 导出执行器在图片生成后、平台写入后和处理下一请求前检查取消。平台即使迟到返回，也不能在 Store 释放后启动下一次写入或发布完成反馈；已经开始且不响应取消的外部写入无法撤回。
- 完成反馈仍交由控制器处理。复制和保存均在原子更新内检查歌曲、会话及请求编号；旧结果沿用 `operationNotices`。保存去重记录仍由控制器维护，结束通知通过比较请求身份清除，旧任务不能解除新请求的去重。
- 保留现有错误／取消文案、失败后继续队列、失败重试及保存去重规则。页面、数据库、持久化配置格式和字体偏好写入流程未改。

## 预览提交并发修复

2026-10-23 完成。修复旧预览尚未发布状态时，选句／模板改动后再改回、新预览已经完成，旧调度仍能重新设置“生成中”或清除新错误的问题。

- `PlayerState` 保留最近接受的预览请求版本；完成、编辑、清空和结束会话只清除活动请求编号，不重置该版本。
